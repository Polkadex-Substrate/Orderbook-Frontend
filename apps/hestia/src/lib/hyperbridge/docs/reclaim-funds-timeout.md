# Hyperbridge Cross-Chain Bridge Integration

## Overview

This document covers the full Hyperbridge integration for the Sepolia → Polkadex testnet bridge, including the complete transfer flow, status polling, BE sync logic, timeout/refund flow, all implementation decisions made, known limitations, and testing status.

**Network**: Gargantua testnet  
**Route**: Sepolia (EVM) → Polkadex Testnet (Substrate)  
**Protocol**: ISMP (Interoperable State Machine Protocol) via `@hyperbridge/sdk`

---

Browser

  ├── /thea page (bridge UI)

## Transfer Flow (Sepolia → Polkadex)

### Step 1: User submits transfer (`ethereumToSubstrate.ts`)

1. User selects token, amount, and Polkadex recipient address in the bridge form.
2. `transferTokens()` is called:
   - Encodes the Polkadex SS58 address as a hex `bytes32`.
   - If token is not native ETH (`isWeth=false`): checks WETH allowance, approves `maxUint256` to the HFT contract if needed.
   - Calls `WrappedHFT.quote(sendParams)` to get the native ETH fee required for ISMP dispatch.
   - Calls `WrappedHFT.send(sendParams, { value: txValue })` — the token is locked in the HFT contract, and an ISMP `PostRequest` is emitted.
3. The tx receipt is parsed for the `PostRequestEvent` log → `postRequestCommitment()` derives the **commitment hash** (32-byte identifier for this request).
4. `{ hash, commitment }` is returned to the UI and saved to the Polkadex backend.

### Step 2: Protocol relay

The Hyperbridge protocol relays the request through the following stages:

#### Normal delivery path (success)

| Stage | What happens | Stored in indexer? |
|---|---|---|
| `SOURCE` | PostRequest event emitted on Sepolia | Yes |
| `SOURCE_FINALIZED` | Sepolia block with tx finalized | No (computed by SDK) |
| `HYPERBRIDGE_DELIVERED` | Request delivered to Hyperbridge | Yes |
| `HYPERBRIDGE_FINALIZED` | Hyperbridge finalized the delivery | No (computed by SDK) |
| `DESTINATION` | Request executed on Polkadex, tokens minted | Yes |

#### Timeout path (failure / refund)

| Stage | What happens | Stored in indexer? |
|---|---|---|
| `PENDING_TIMEOUT` | Request passed timeout deadline | No (detected by wall-clock vs timeoutTimestamp) |
| `DESTINATION_FINALIZED_TIMEOUT` | Polkadex acknowledged timeout | No (computed by SDK) |
| `HYPERBRIDGE_TIMED_OUT` | Timeout recorded on Hyperbridge | Yes |
| `HYPERBRIDGE_FINALIZED_TIMEOUT` | Timeout proof generated, calldata ready | No (generated by SDK's WS stream) |
| `TIMED_OUT` | Refund tx submitted on Sepolia, tokens unlocked | Yes |

> **Critical**: The Gargantua indexer only stores 5 statuses: `SOURCE`, `HYPERBRIDGE_DELIVERED`, `DESTINATION`, `HYPERBRIDGE_TIMED_OUT`, `TIMED_OUT`. All other stages are either computed by the SDK (requires WS connections) or detected by local heuristics (timestamp comparison).

## Status Polling (`useHyperbridgeStatus.ts`)

The hook polls every 30 seconds via `queryPostRequest()` from `@hyperbridge/sdk`.

### Why a CORS proxy?

The Gargantua indexer (`https://gargantua.indexer.polytope.technology`) does not send CORS headers. Direct browser requests are blocked. The solution is:

```
Browser → POST /api/hyperbridge → Next.js server → Gargantua indexer
```

`apps/hestia/src/app/api/hyperbridge/route.ts` is the proxy. `useHyperbridgeStatus.ts` uses `window.location.origin + "/api/hyperbridge"` as the client URL.

### Status parsing logic

`parseStatuses()` iterates all status nodes returned by the indexer and finds the highest stage in each progression (delivery and timeout). It also synthesizes `PENDING_TIMEOUT` client-side:

```
if (timeoutTimestamp > 0 && Date.now()/1000 >= timeoutTimestamp && !delivered) {
  → synthesize PENDING_TIMEOUT
}
```

This ensures the backend is updated to `TIMEDOUT` as soon as the timeout deadline passes, even before Hyperbridge has processed the timeout on-chain.

### Returned flags

| Flag | True when |
|---|---|
| `isDelivered` | `deliveryStage === "DESTINATION"` |
| `isTimedOut` | Any timeout stage is present |
| `isRefundable` | `timeoutStage === "HYPERBRIDGE_TIMED_OUT"` (indexer confirms it; SDK can generate proof) |
| `isRefunded` | `timeoutStage === "TIMED_OUT"` (refund tx already submitted) |

## BE Status Sync (`ClaimRefundButton`)

The Polkadex backend (`updateCrossChainTransactionStatus`) accepts three statuses: `PENDING`, `TIMEDOUT`, `COMPLETED`.

Three independent `useEffect` hooks each with their own `useRef` guard handle every possible transition:

| Effect | Condition | BE update |
|---|---|---|
| Effect 1 | `BE=PENDING` + `hbStatus.isDelivered` | `PENDING → COMPLETED` |
| Effect 2 | `BE=PENDING` + `hbStatus.isTimedOut` | `PENDING → TIMEDOUT` |
| Effect 3 | `BE=TIMEDOUT` + `hbStatus.isRefunded` | `TIMEDOUT → COMPLETED` |

**Why three separate `useRef` guards?** A single shared guard would block Effect 3 if Effect 2 already set it to `true`. For example: a request goes PENDING → TIMEDOUT (Effect 2 fires, sets `syncing=true`) → later TIMED_OUT (refund confirmed, Effect 3 tries to fire but guard blocks it). Three separate refs prevent this cross-contamination.

After each successful BE update, `queryClient.invalidateQueries` refetches the transactions list to reflect the new status in the UI.

## Claim Refund Flow (`claimRefund.ts`)

When the user clicks "Claim Refund":

1. **Reads `hostParams.handler`** from the ISMP host contract on Sepolia.  
   This is the ISMP message handler — the correct target for submitting timeout proofs. The `ismpHost` address itself is **not** the submission target.

2. **Builds `IsmpClient`** with three chain connections:
   - `EvmChain.fromParams(...)` — Sepolia (HTTP RPC only)
   - `SubstrateChain.connect(wsUrl: polkadex.wsUrl)` — Polkadex destination (WS)
   - `SubstrateChain.connect(wsUrl: "wss://gargantua.polytope.technology")` — Hyperbridge node (WS)

3. **Streams `postRequestTimeoutStream(commitment)`** — an async generator that yields timeout stages. The SDK queries chain state over WS to compute the proof. When the stream yields `HYPERBRIDGE_FINALIZED_TIMEOUT`, `update.metadata.calldata` contains the fully constructed EVM calldata.

4. **Submits the calldata** via `walletClient.sendTransaction({ to: hostParams.handler, data: calldata })`.

5. **Effect 3** in `ClaimRefundButton` detects the resulting `TIMED_OUT` status on next polling cycle and updates the BE to `COMPLETED`.

### Why `claimRefund` accepts `commitment`, not `calldata`

The Gargantua indexer does **not** store calldata in status metadata. The `HYPERBRIDGE_FINALIZED_TIMEOUT` stage is never written to the indexer — it exists only in the SDK's WS stream. Therefore, calldata cannot be pre-fetched and must be generated on-demand by creating a full `IsmpClient` at claim time.

## Known Limitations and Pending Work

### 1. Refund flow is untested end-to-end

**Status**: Not tested  
**Reason**: No Sepolia → Polkadex test transaction has yet reached the `HYPERBRIDGE_TIMED_OUT` stage in the Gargantua indexer. The transfer timeout is 3600 seconds (1 hour), and test transactions have not remained undelivered long enough to enter the timeout flow.

**What needs to happen to test**:
- Submit a transfer that is intentionally not delivered (e.g., by using a destination address the relayer cannot execute on, or by waiting out the 1-hour timeout).
- Confirm the BE status transitions PENDING → TIMEDOUT via the auto-sync effect.
- Confirm the "Claim Refund" button appears (requires `HYPERBRIDGE_TIMED_OUT` in the indexer).
- Click "Claim Refund" and confirm:
  - The `postRequestTimeoutStream` stream yields `HYPERBRIDGE_FINALIZED_TIMEOUT` with valid calldata.
  - The transaction is submitted to `hostParams.handler` on Sepolia.
  - The tokens are returned to the sender's Sepolia address.
  - The indexer reflects `TIMED_OUT`.
  - Effect 3 fires and updates the BE to `COMPLETED`.

### 2. `claimRefund` blocks until proof is generated

**Status**: Known UX issue  
**Detail**: `postRequestTimeoutStream` is a long-running WS stream. Once the user clicks "Claim Refund", the button shows a "Claiming…" spinner and the function may block for several minutes while waiting for the Hyperbridge node to generate the timeout proof. There is no cancellation mechanism or timeout.

**Improvement path**: Move proof generation to a background process or show a progress indicator per stream stage. Currently the button disables and shows "Claiming…" for the entire duration.

### 3. `IsmpClient` WS connections in `claimRefund` are ephemeral

**Status**: Acceptable for current scale  
**Detail**: `claimRefund` creates fresh `SubstrateChain.connect()` WS connections on every click. These are not reused between calls. For a production app, a shared singleton (similar to `getIndexer()` in `ethereumToSubstrate.ts`) would be preferable.

### 4. Only Sepolia → Polkadex route is implemented

**Status**: By design for now  
**Detail**: `claimRefund.ts`, `useHyperbridgeStatus.ts`, and `ethereumToSubstrate.ts` all hardcode the Gargantua/Sepolia/Polkadex chain config. If a second route (e.g., Polkadex → Sepolia, or mainnet) is added, these files must be refactored to accept chain config as parameters.

### 5. No mainnet deployment

**Status**: Pending  
**Detail**: All addresses, RPC URLs, and chain IDs are for Sepolia testnet and Polkadex testnet. Mainnet support requires new environment variables and contract addresses from the Hyperbridge team.

## Common Debugging Reference

### Indexer returning 522 / connection timeout
- Check `NEXT_PUBLIC_BRIDGE_INDEXER_URL` — must be `https://gargantua.indexer.polytope.technology`
- After changing `.env.local`, restart the dev server (`yarn dev`)
- The proxy at `/api/hyperbridge/route.ts` hot-reloads its hardcoded fallback without restart

### Status polling returns null repeatedly
- The commitment hash may not be indexed yet (can take 1–2 minutes after the source tx)
- Check browser network tab for calls to `/api/hyperbridge` — 200 with `{ data: { requestV2s: { nodes: [] } } }` means not indexed yet

### "Claim Refund" button never appears
- The button appears only when `hbStatus.isRefundable === true`, which requires the Gargantua indexer to show `HYPERBRIDGE_TIMED_OUT`
- `HYPERBRIDGE_TIMED_OUT` only appears after the Hyperbridge protocol has processed the timeout on-chain — this can take 30 minutes to hours after the 1-hour timeout deadline passes
- Check the Hyperbridge explorer for the commitment hash to see current on-chain status

### Wrong Hyperbridge WS URL
- Correct URL: `wss://gargantua.polytope.technology`
- Wrong URL (was previously used): `wss://gargantua.indexer.polytope.technology` — this is the indexer HTTP endpoint, not the Hyperbridge node WS

### BE mutation not firing
- The mutation fires only when `hbStatus` is non-null AND the specific flag (`isDelivered`, `isTimedOut`, `isRefunded`) is `true`
- If `hbStatus` is always `null`, the indexer is not returning data — check the CORS proxy and indexer URL
- Each sync direction has its own `useRef` guard — if the guard is set, the mutation will not re-fire even if the component re-renders
